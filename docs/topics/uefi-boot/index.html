💭 考えてみましょう

コンピュータの電源を入れた瞬間、メモリは完全に空っぽです。
プログラムを実行するにはメモリにコードを読み込む必要がありますが、
「メモリにプログラムを読み込むプログラム」は一体誰が、どこから読み込むのでしょうか？

🌟 身近な例で考えると...

コンピュータの起動は、朝起きてから出社するまでの準備によく似ています：

この一連の「起床から出社まで」を管理してくれる「朝の執事」のような存在、それがUEFIです。

🎯 なぜこの技術が必要なのか

  • ブートストラップ問題の解決: 「最初のプログラムを読み込むプログラム」が必要
  • ハードウェアの多様性: 異なるメーカー・仕様のハードウェアを統一的に扱う
  • セキュリティの確保: 信頼できるソフトウェアのみを起動させる
  • 効率的な初期化: 複雑な現代のハードウェアを適切な順序で初期化
  • OSの独立性: 特定のOSに依存しない標準的なインターフェース

📋 UEFIとは何か

UEFI (Unified Extensible Firmware Interface) は、コンピュータの電源投入からOSの起動までを管理する現代的なファームウェア仕様です。

🏛️ 従来のBIOS

  • 16ビットモードで動作
  • 1MBメモリ制限
  • 2TBディスク制限
  • テキストベースUI
  • 拡張性に乏しい

⚡ 現代のUEFI

  • 32/64ビットモードで動作
  • 大容量メモリ対応
  • 9ZB超ディスク対応
  • グラフィカルUI
  • モジュラー設計

なぜUEFIが必要なのか？

  • 🔒 セキュリティ強化: Secure Boot、TPM連携
  • 🚀 高速起動: 並列初期化、最適化されたドライバ
  • 🔧 拡張性: プロトコルベースの設計
  • 🖥️ 現代的UI: マウス操作、高解像度対応

🚪 ブートサービスからの離脱

OSが制御を取得する前に、UEFIブートサービスを終了する必要があります：

⚠️ 重要なポイント

  • メモリマップの取得: 最新の状態を確認
  • ExitBootServices呼び出し: ブートサービス終了
  • 失敗時の再試行: メモリ状態変化への対応
  • ランタイムサービス: 継続利用可能
// ブートサービス終了処理 pub fn exit_from_efi_boot_services( image_handle: EfiHandle, efi_system_table: &EfiSystemTable, memory_map: &mut MemoryMapHolder, ) {
loop {
// 最新のメモリマップを取得
let status = efi_system_table.boot_services.get_memory_map(memory_map);
assert_eq!(status, EfiStatus::Success);
// ブートサービス終了を試行
let status = (efi_system_table.boot_services.exit_boot_services)(
image_handle,
memory_map.map_key
);
if status == EfiStatus::Success { break; } // 失敗した場合は再試行（メモリマップが変更された可能性） } }

🔧 WasabiOSでの実装の流れ

実際のWasabiOSでは、以下の順序でUEFI機能を活用しています：

📝 初期化段階

  1. システムテーブル取得
    EfiSystemTableからブートサービスにアクセス
  2. グラフィックス初期化
    init_vram()でVRAM情報を取得
  3. メモリマップ取得
    システムメモリ構成を把握

🚀 OS起動段階

  1. 必要な初期化完了
    フォントシステム、描画機能など
  2. ブートサービス終了
    exit_from_efi_boot_services()
  3. OS本体実行
    独自のメモリ管理、タスク管理へ

重要な設計判断：

  • 🎯 最小限のUEFI依存: 必要な機能のみ使用
  • 🔒 安全な型定義: Rustの型システムでUEFI構造体を表現
  • ⚡ 効率的なメモリ管理: UEFIメモリマップを活用
  • 🖥️ 直接VRAM操作: 高速な描画処理

🎯 まとめ

UEFIブートプロセスは現代のコンピュータシステムの基盤となる重要な技術です。

✅ UEFIの利点

  • モダンなアーキテクチャ
    64ビット、大容量対応
  • 豊富なプロトコル
    グラフィックス、ネットワーク等
  • セキュリティ機能
    Secure Boot、TPM連携
  • 開発効率
    標準化されたAPI

⚠️ 注意点

  • 複雑性
    BIOSより学習コストが高い
  • 実装依存
    ベンダー固有の動作
  • デバッグ困難
    低レベルでの問題解析
  • 互換性
    レガシーシステムとの差異
