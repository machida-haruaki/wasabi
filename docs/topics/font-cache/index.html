🚀 フォントキャッシュの動作解説

📋 概要

フォントデータの読み込み方法を毎回ファイル解析からキャッシュ方式に変更しました。

🐌 変更前（遅い）

  • 文字を描画するたびにファイル全体を解析
  • 時間計算量: O(n)
  • メモリ使用量: 少ない

⚡変更後（速い）

  • 初回のみファイル解析、以降は配列アクセス
  • 時間計算量: O(1)
  • メモリ使用量: 多い（トレードオフ）

🏗️ データ構造の宣言

static mut FONT_CACHE: Option<[[[char; 8]; 16]; 256]> = None;

3次元配列の構造:

  • [256]: ASCII文字256文字分
  • [16]: 各文字の高さ16ピクセル
  • [8]: 各行の幅8文字

🔍 変更前の処理フロー

毎回ファイル解析方式

  1. 文字 'A' を描画したい
  2. font.txtを最初から読み込み開始
  3. 「0x41」（'A'のASCII）を探して順次検索
  4. 見つかったら16行分のデータを読み取り
  5. フォントデータを返す

問題点: 文字を描画するたびに同じ処理を繰り返す

⚡ 変更後の処理フロー

キャッシュ方式

初回アクセス時:

  1. FONT_CACHE が None かチェック
  2. None なので初期化開始
  3. font.txt全体を一度だけ解析
  4. 全256文字分のデータを配列に格納
  5. FONT_CACHE を Some(配列) に設定

2回目以降:

  1. FONT_CACHE が Some(配列) なのでそのまま使用
  2. font[文字コード] で直接アクセス

🔧 get_or_insert_with の動作

FONT_CACHE.get_or_insert_with(|| { // 初期化処理（初回のみ実行） let mut font = [[['*'; 8]; 16]; 256]; // ... ファイル解析処理 ... font })

Option<T> の状態変化

初期状態: None
初期化後: Some([配列データ])

🎯 まとめ

キャッシュの利点

  • ✅ 高速アクセス: O(1)の配列アクセス
  • ✅ CPU効率: ファイル解析処理の削減
  • ✅ 予測可能: 初回以降は一定の処理時間

トレードオフ

  • ⚠️ メモリ使用量: 256文字分のデータを常駐
  • ⚠️ 初期化コスト: 初回アクセス時に全データ読み込み

結論: フォント描画が頻繁に行われるグラフィックシステムでは、メモリを使ってでも速度を優先する設計が適切です。
